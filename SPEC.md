# Спецификация nRPC v0.1.0

## 1. Обзор

**nRPC** — легковесный, высокопроизводительный фреймворк для удаленного вызова процедур (RPC), предназначенный для управления лабораторным и промышленным оборудованием. Фреймворк реализует строгую синхронную модель взаимодействия "Запрос-Ответ" (Request-Response) поверх TCP.

Серверное ядро реализовано на C++23 с использованием паттерна Reactor (неблокирующий I/O) и пула воркеров для изоляции блокирующих вызовов драйверов оборудования. Для передачи данных используется бинарный протокол с выровненными структурами, оптимизированный для минимальных накладных расходов и предсказуемого парсинга.

## 2. Сетевой протокол

### 2.1. Базовые правила
1.  **Порядок байтов:** Все многобайтовые числовые поля передаются в сетевом порядке байтов (Big-Endian).
2.  **Фрейминг:** Границы сообщений определяются полем `Payload Size`. Чтение из TCP-потока строго двухэтапное: 16 байт заголовка, затем `Payload Size` байт нагрузки.
3.  **Модель:** Один запрос всегда генерирует ровно один ответ. Мультиплексирование и потоковая передача (Streaming) не поддерживаются.

### 2.2. Заголовок запроса (16 байт)

| Смещение | Размер (байт) | Поле             | Описание                                                        |
| :--- | :--- | :--- | :--- |
| 0        | 1             | Magic            | `0xF0` (Идентификатор запроса)                                 |
| 1        | 1             | Version          | Версия протокола (`0x01`)                                       |
| 2        | 1             | Function Index   | Индекс вызываемой функции в таблице диспетчера сервера          |
| 3        | 1             | Variables Count  | Количество передаваемых переменных (максимум 255)               |
| 4        | 4             | Payload Size     | Общий размер нагрузки (таблица переменных + сырые данные)       |
| 8        | 4             | Timeout (ms)     | Таймаут для блокирующих операций на стороне сервера (0 = бесконечно) |
| 12       | 4             | Reserved         | Зарезервировано (выровнено нулями)                              |

### 2.3. Заголовок ответа (16 байт)

| Смещение | Размер (байт) | Поле             | Описание                                                        |
| :--- | :--- | :--- | :--- |
| 0        | 1             | Status Code      | `0x00` (Успех), `0x01` (Ошибка)                                 |
| 1        | 1             | Version          | Эхо версии из запроса                                           |
| 2        | 1             | Function Index   | Эхо индекса функции из запроса                                  |
| 3        | 1             | Variables Count  | Количество переменных в ответе (в случае ошибки равно 0)        |
| 4        | 4             | Payload Size     | Общий размер нагрузки ответа                                    |
| 8        | 4             | Error Code       | Код ошибки бэкенда (если Status Code = `0x01`, иначе 0)         |
| 12       | 4             | Reserved         | Зарезервировано (выровнено нулями)                              |

### 2.4. Таблица переменных (16 байт на запись)
Записи следуют сразу за заголовком. Смещения выровнены по степеням двойки для оптимизации парсинга.

| Смещение | Размер (байт) | Поле             | Описание                                  |
| :--- | :--- | :--- | :--- |
| 0        | 1             | Data Type        | Код типа данных (см. 2.5)                 |
| 1        | 3             | Reserved         | Выравнивание                              |
| 4        | 4             | Total Data Size  | Общий размер данных переменной в байтах   |
| 8        | 4             | Element Count    | Количество элементов в переменной         |
| 12       | 4             | Reserved         | Выравнивание до 16 байт                   |

Сразу за таблицей переменных следуют сырые байты данных всех переменных в том же порядке, что и записи в таблице.

### 2.5. Типы данных

| Имя типа | Код   | Размер элемента | Описание                                                                                   |
| :--- | :--- | :--- | :--- |
| `null`   | `0x00`| 0               | Пустое значение.                                                                           |
| `int8`   | `0x01`| 1               | Знаковое 8-бит                                                                             |
| `uint8`  | `0x02`| 1               | Беззнаковое 8-бит                                                                          |
| `int16`  | `0x03`| 2               | Знаковое 16-бит                                                                            |
| `uint16` | `0x04`| 2               | Беззнаковое 16-бит                                                                         |
| `int32`  | `0x05`| 4               | Знаковое 32-бит                                                                            |
| `uint32` | `0x06`| 4               | Беззнаковое 32-бит                                                                         |
| `int64`  | `0x07`| 8               | Знаковое 64-бит                                                                            |
| `uint64` | `0x08`| 8               | Беззнаковое 64-бит                                                                         |
| `float32`| `0x09`| 4               | IEEE 754 одинарной точности                                                                |
| `float64`| `0x10`| 8               | IEEE 754 двойной точности                                                                  |
| `bool`   | `0xA0`| 1               | `0x00` — false, `0x01` — true                                                              |
| `string` | `0xA1`| 1               | UTF-8 строка. Обязателен нуль-терминатор `\0`, который входит в Total Data Size и Element Count. |
| `bytes`  | `0xA2`| 1               | Сырые бинарные данные. Длина определяется полем Total Data Size.                           |

## 3. Архитектура сервера

### 3.1. Потоковая модель
Сервер использует паттерн Reactor для разделения сетевого I/O и обработки логики.
*   **Event Loop (I/O Thread):** Принимает TCP-соединения, использует системные вызовы мультиплексирования (`epoll`/`IOCP`) для неблокирующего чтения и записи. Отвечает за парсинг заголовков и маршрутизацию.
*   **Worker Pool:** Пул потоков для выполнения бизнес-логики. Воркер извлекает запрос из очереди, вызывает блокирующий API драйвера оборудования (например, `sp_blocking_read` или `viRead`), дожидается результата, формирует ответ и передает его обратно в Event Loop для отправки по сети.

### 3.2. Управление памятью (Arena Allocator)
Для выделения памяти под ответы используется Arena Allocator.
*   При поступлении запроса воркер получает арену фиксированного размера.
*   Выделение памяти внутри бэкенда происходит за O(1) (сдвиг указателя с выравниванием).
*   После отправки ответа клиенту память арены сбрасывается разом. Вызовы `free` для отдельных переменных отсутствуют, что исключает фрагментацию и утечки.

### 3.3. Менеджер ресурсов (Resource Manager)
Потокобезопасный реестр открытых дескрипторов оборудования.
*   Связывает абстрактный идентификатор (`handle_id`) и идентификатор клиента с RAII-обертками нативных дескрипторов ОС (например, `ViSession`, `sp_port*`).
*   При разрыве TCP-соединения с клиентом, менеджер автоматически вызывает деструкторы всех связанных RAII-оберток, гарантируя освобождение оборудования (закрытие портов, сессий).

### 3.4. Диспетчер (Dispatcher)
Статическая таблица маршрутизации. Сопоставляет `Function Index` из заголовка запроса с конкретным методом C++ бэкенда.

## 4. Интерфейс бэкендов

Бэкенды реализуются на C++23. Взаимодействие с ядром сервера базируется на концепциях (C++23 Concepts) для статического полиморфизма.

1.  **Обработка ошибок:** Используется `std::expected<T, BackendError>`. Исключения в бэкендах перехватываются на уровне диспетчера и конвертируются в ответ с Status Code `0x01`.
2.  **Передача данных:** Используются невладеющие представления `std::span<const std::byte>` для входных данных и `std::span<std::byte>` для выходных буферов из арены.
3.  **RAII:** Все дескрипторы оборудования обязаны реализовывать концепт `NrpcHandle` (наличие метода `close()` и запрещенное копирование).
4.  **Блокирующие вызовы:** Бэкенды имеют право вызывать блокирующие функции драйверов, так как их выполнение изолировано в потоках Worker Pool.

## 5. Python-клиент

Для версии 0.1.0 клиент реализуется как **строго синхронная** библиотека.
*   Взаимодействие осуществляется через блокирующие сокеты.
*   Метод `call(function_index, args, timeout)` отправляет запрос, блокирует поток выполнения до получения полного ответа (согласно `Payload Size`) и возвращает распарсенный объект ответа.
*   Конвертация данных из Network Byte Order в родной формат Python выполняется на этапе парсинга ответа.

---

### 5.1. Discovery сервера

Встроенная функция `2` принимает пустой список аргументов и возвращает пять
переменных: `STRING` версии сервера, scalar `UINT8` версии wire-протокола,
`STRING` платформы (`windows`/`linux`), `STRING` архитектуры и отсортированный
массив `UINT8` всех зарегистрированных function indices. Добавление функции не
изменяет wire-версию `0x01`. Ошибка `4` означает, что discovery получил
неожиданные аргументы.

## 6. Логирование (Logger)

Сервер должен быть оснащен потокобезопасным логгером для трассировки запросов и диагностики работы оборудования.

### 6.1. Общие требования
*   **Потокобезопасность:** Логгер должен корректно обрабатывать одновременную запись из потоков Event Loop и Worker Pool без искажения строк (использование мьютексов, lock-free очередей или thread-local буферов с последующим слиянием).
*   **Уровни логирования:** `ERROR`, `WARN`, `INFO`, `DEBUG`.

### 6.2. Режим DEBUG
При компиляции в режиме `DEBUG` логгер обязан выводить дампы бинарного трафика для контроля корректности формата пакетов и анализа проблем на уровне протокола.
*   **Формат дампа:** Шестнадцатеричный дамп (Hex dump) полного пакета, включая заголовок, таблицу переменных и полезную нагрузку.
*   **Логируемые события:**
    *   `RX Request`: Дамп полученного от клиента запроса.
    *   `TX Response`: Дамп ответа, отправляемого клиенту (в том числе при ошибках).
*   Дампы должны сопровождаться расшифровкой ключевых полей заголовка (Function Index, Payload Size, Status Code) в человекочитаемом виде в той же строке лога.

## 7. Требования к тестированию (Test Coverage)

Все ключевые компоненты nRPC должны быть покрыты модульными и интеграционными тестами. Использование фреймворков (Catch2 / GoogleTest) обязательно.

### 7.1. Модульные тесты (Unit Tests)
*   **Protocol Codec:** Тестирование сериализации и десериализации. Проверка корректной конвертации Endianness для всех поддерживаемых типов данных, проверка выравнивания, обработка невалидных пакетов (усеченные заголовки, несовпадение Payload Size).
*   **Arena Allocator:** Тестирование выделения памяти O(1), обработки исчерпания памяти (OOM) и корректного сброса (reset) без утечек.
*   **Resource Manager:** Тестирование регистрации и поиска дескрипторов. Тестирование логики автоматической очистки (`cleanup_client`): эмуляция отключения клиента и проверка вызова деструкторов (RAII) для связанных дескрипторов.
*   **Dispatcher:** Проверка корректности маршрутизации индексов функций и передачи контекста запрос-ответ.

### 7.2. Интеграционные тесты
*   **Клиент-Серверное взаимодействие:** Тестирование полного цикла с использованием синхронного Python-клиента и mock-бэкендов на сервере.
*   **Блокирующие вызовы:** Проверка того, что долгий блокирующий вызов в одном воркере не препятствует обработке других запросов сервером.
*   **Таймауты:** Проверка корректного возврата ошибки с кодом таймаута, если операция оборудования превышает значение поля `Timeout` из заголовка запроса.

### 7.3. Стресс-тестирование
*   Многопоточная отправка запросов от нескольких клиентов к одному серверу. Проверка отсутствия состояния гонки (data race) и взаимных блокировок (deadlock) в логгере, менеджере ресурсов и при работе с аренами.
